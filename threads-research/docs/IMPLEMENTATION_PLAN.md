# 開發計畫（個人版）

本計畫把 PRD 拆成可以逐步完成的步驟。每一步都有**驗收標準**，完成後再進行下一步。

- 階段一（步驟 1～7）：單篇分析＋靜態網頁前台，**完全不需要 Threads API 也能完成**，先用手動匯入與範例資料開發。
- 階段二（步驟 8～9）：串接 Threads 官方 API。
- 階段三（步驟 10～12）：研究專案與洞察庫。

---

## 步驟 1：專案骨架與資料格式

**要做的事**

- 建立 `scripts/`、`site/`、`data/` 的基本結構與 `requirements.txt`。
- 完成 `schemas/` 中的 JSON Schema：
  - `snapshot.schema.json`（已有草稿）：一次收集的原始資料。
  - `run.schema.json`：一次分析的結果（類型判斷、收集範圍、內容篩選統計、模式萃取結果、摘要、結論卡）。
  - `index.schema.json`：報告庫清單。
  - `showcase_item.schema.json`（已有草稿）：M1 的單一項目。
- 寫 `scripts/validate.py`：用 schema 驗證任一個 JSON 檔。

**驗收標準**

- `python scripts/validate.py <檔案>` 對符合與不符合格式的檔案，分別回報通過與錯誤原因。
- 每個 schema 都有 `schema_version` 欄位。

---

## 步驟 2：範例資料與手動匯入

**要做的事**

- 在 `data/samples/` 建立一份**虛構的**範例貼文串：「大家都用 Claude 做出了什麼工具？」，約 60 則留言，包含：
  - 分享工具的留言（有的附連結、有的分好幾則補充）
  - 追問、求連結、稱讚、標記朋友等應被排除的留言
  - 不同人分享同一個工具（測試去重）
  - 名稱相似但其實不同的工具（測試不該合併）
- 寫 `scripts/import_manual.py`：把使用者提供的 CSV 或 JSON（欄位見 PRD 附錄 B）轉成符合 `snapshot.schema.json` 的檔案。

**驗收標準**

- 範例資料能通過 schema 驗證，並能重建出正確的回覆樹。
- 範例資料中所有帳號與內容都是虛構的。

---

## 步驟 3：第 1 層前處理（一般程式，不用 AI）

**要做的事**：`scripts/preprocess.py`

- 基本統計：總留言數、參與人數、平均與最大深度、原作者回覆次數。
- 第 1～2 層去重：相同 `post_id`、同一人重複貼的相同內容。
- 明顯閒聊的預過濾：純表情、只有標記帳號、「+1」、「推」等（用規則判斷；不確定的一律留給 Claude 判斷）。
- 需求訊號的初步計數：「求連結」「我也想要」「怎麼做的」等關鍵字。
- 萃取留言中的連結。

**驗收標準**

- 對範例資料執行後，統計數字正確；被預過濾的留言都真的是閒聊（寧可少過濾，不可誤刪）。

---

## 步驟 4：`/analyze-thread` 指令（M1 徵集型）

**要做的事**：完善 `.claude/commands/analyze-thread.md`，讓 Claude Code 能依指令完成：

1. 類型判斷（輸出類型、信心、理由），並**先向使用者確認**再繼續。
2. 收集範圍判斷（PRD 4.2）。
3. 內容篩選：收錄／合併／排除，排除前統計訊號（PRD 4.3.1）。
4. 依 `profiles/showcase.yaml` 萃取項目、跨留言合併、第 3～4 層去重、分類、關注度評分、需求缺口、心得彙整。
5. 產出結論卡與摘要。
6. 寫出 `data/threads/{thread_id}/runs/{run_id}.json`，通過 schema 驗證，並更新 `data/index.json`。

**驗收標準**

- 對範例資料執行，工具清單與人工標註相比：召回率 ≥ 90%、沒有任何無法在原留言找到依據的內容。
- 應合併的有合併、名稱相似但不同的沒有被合併。
- 每個項目都附來源 `post_id`。

---

## 步驟 5：網頁前台（靜態版）

**要做的事**：`site/index.html`、`site/app.js`、`site/style.css`

- **報告庫頁**：讀 `data/index.json`，表格列出所有報告，可以排序、篩選、搜尋。
- **單篇報告頁**：依 PRD 5.5 的四層呈現：
  1. 結論卡
  2. 核心表格（M1：工具清單表，可排序篩選；分類分布；Claude 使用方式；最受關注；心得；需求缺口）
  3. 少量圖表（分類分布用橫條圖）
  4. 證據：點數字或項目可以看到來源留言；研究方法與限制
- **待處理區**：列出「已排除清單」與「可能重複」，可以在頁面上標記（階段一先存在瀏覽器，並可匯出成 JSON 讓 Claude Code 套用）。
- 支援手機瀏覽與深色模式；所有文字為繁體中文。

**驗收標準**

- 執行 `python -m http.server 8000` 後，在 `http://localhost:8000/site/` 能看到範例報告。
- 新增一份 run JSON 並更新 index 後，重新整理頁面就會出現，不需要改前台程式。

---

## 步驟 6：M4 品牌／產品回饋型與抽樣收集

**要做的事**

- `profiles/brand_feedback.yaml`（已有草稿）與對應的報告區塊。
- 實作 PRD 4.2 的逐步抽樣：以 50 則為起點，每次加 50 則，收斂才停；在 run 中記錄抽樣過程與停止原因。

**驗收標準**

- 用較大的範例資料回測：抽樣結果與全量結果的各類比例差距 ≤ 5 個百分點。

---

## 步驟 7：匯出

- 報告匯出 Markdown（結論卡＋核心表格）與 Excel（多工作表）。
- 原始資料匯出 CSV（PRD 附錄 B）。

---

## 步驟 8：Threads 官方 API 技術評估（需要使用者操作）

**要做的事**

- 協助使用者在 Meta 開發者平台建立 App、申請權限、以自己的帳號授權。
- 實測並記錄在 `docs/API_FINDINGS.md`：
  - 自己貼文的回覆（含多層回覆）能否完整取得
  - 他人公開貼文的回覆能取得多少
  - 關鍵字搜尋能否使用、回傳數量與時間範圍
  - 他人公開帳號的貼文能否讀取
  - 速率限制
- 存取權杖只放在 `.env`，不進 Git。

**驗收標準**：`docs/API_FINDINGS.md` 回答以上每一項，並據此更新 PRD 第 7 節與待決問題。

---

## 步驟 9：API 收集器

- `scripts/collect_thread.py`：輸入貼文網址，收集主貼文與回覆，產生 snapshot；支援分頁、退避重試、續傳。

---

## 步驟 10～12：研究專案與洞察庫

- **步驟 10**：帳號經營分析（PRD 5.4）與 `/analyze-account` 指令；帳號頁。
- **步驟 11**：主題研究（PRD 5.3）與 `/research-topic` 指令。
- **步驟 12**：洞察庫（PRD 11.4）：跨報告的工具總表、高互動公式庫、市場缺口庫。

每一步開始前，先依 PRD 對應章節寫出細部規格並與使用者確認。
