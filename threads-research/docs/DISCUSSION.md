# 需求討論紀錄與決策

本文件整理 PRD 形成過程中的討論，說明每個設計「為什麼這樣做」。規格細節以 `PRD.md` 為準。

---

## 1. 起點：分析一篇 Threads 貼文串（PRD v0.1）

**需求**：針對某一篇 Threads 貼文，收集它的內容並研究分析。

**當時的設計**：收集主文與所有層級的回覆，做摘要、情緒、立場、主題分群，產出報告與可匯出的資料。

**最關鍵的風險是資料來源**：

- Threads 官方 API 最合規，但完整回覆多半只能拿到**自己帳號的貼文**。
- 在伺服器端自動擷取別人的貼文，可能違反平台的服務條款。
- 因此 MVP 採用「官方 API（自己的貼文）＋手動匯入」。

---

## 2. 不同類型的貼文，要研究不同的東西（PRD v0.2）

**需求**：像「大家用 Claude 開發出了什麼工具？」這種貼文，重點是收集大家的想法和作品，而不是行銷用的語言情緒。要依貼文主題決定研究方向。

**決定**：先判斷貼文類型，再套用對應的分析模式。

| 模式 | 研究重點 |
| --- | --- |
| M1 徵集／作品分享型 | 大家做了什麼、解決什麼問題、怎麼做的 |
| M2 提問求助型 | 大家推薦什麼答案、理由、共識 |
| M3 意見討論／爭議型 | 有哪些立場與論點 |
| M4 品牌／產品回饋型 | 情緒、客訴、功能需求 |
| M5 新聞／事件反應型 | 反應、補充資訊、疑問 |
| M6 經驗故事型 | 類似經驗、建議 |
| 自訂模式 | 使用者自己輸入研究問題 |

- 系統判斷後由使用者確認，也可以改選或自訂。
- **M1 徵集型是 MVP 第一個模式**，會產出工具清單表（名稱、解決的問題、Claude 使用方式、技術、階段、連結），依用途分類，並整理最受關注的工具、開發心得與需求缺口。
- 「cloud」理解為 **Claude**。

---

## 3. 去重、刪除無關內容、收集範圍（PRD v0.3）

**需求**：

1. 要去重。
2. 只是問答、不屬於要收集的內容，必須刪掉。
3. 只收集前 50 則可能不完整，要判斷是否需要收集全部；但如果是收集情緒，前 50 則或許就夠。

**決定**：

- **前 50 則只用來判斷貼文類型**，不是最終分析的資料。
- **判斷原則**：研究問題是「有哪些」（列舉型）就全量收集；是「多少比例」（比例型，例如情緒）就抽樣。
- **情緒用 50 則的補充**：
  - 平台排在前面的通常是高讚或較早的留言，可能有偏誤，所以盡量依時間與層級分層抽樣。
  - 50 則的誤差約 ±14%，只能看大方向，所以以 50 則為起點，每次加 50 則，比例穩定（連續兩批變化 < 3 個百分點）才停，最多 400 則。
  - 總回覆數 ≤ 300 則時一律全量收集。
- **內容篩選**：收錄／合併（分享者回答問題時補充的細節）／排除。排除的留言刪除，刪除前先統計「求連結」等訊號。為避免誤刪，排除的留言先暫存 7 天可救回。
- **去重四個層級**：同一則留言重複、同一人重複貼、同一人分多則介紹同一個項目、不同人分享同一個項目。不確定的不自動合併。

## 4. 市調功能：從關鍵字或帳號出發（PRD v0.4）

**需求**：幫客戶做某個主題的市調時，提供關鍵字或帳號連結，自動找出相關的討論串，分析對方的經營重點、發文方式與語氣，以及怎麼樣讓更多人想回應。

**決定**：新增「研究專案」（PRD 第 5 節）。

- **主題研究**（關鍵字）：擴充關鍵字 → 找相關貼文 → 排除同名不同義與廣告 → 挑選值得深入分析的貼文 → 討論地圖、大家關心什麼、市場缺口。
- **帳號經營分析**（帳號連結）：
  - 經營重點：內容主軸、主軸 × 互動矩陣。
  - 發文方式：形式、長度、開頭與結尾方式、時段、頻率、作者回覆習慣。
  - 語氣：正式↔口語等向度評分與風格指南。
  - 什麼讓人想回應：以回覆數為主要指標，用「相對互動指數」排除帳號熱度的影響，整理成附樣本數與信心的高互動公式。
  - 競品比較與差異化機會。
- **避免錯誤結論**：貼文少於 30 篇不做互動驅動分析；每條公式的兩組都要 ≥ 10 篇；報告明確提醒「相關不等於因果」。
- **倫理界線**：只分析公開的品牌、創作者、媒體帳號；一般留言者匿名；不推論個人屬性。

## 5. 費用、帳號授權、報告呈現（PRD v0.5）

### 為什麼 AI 會有費用？

分類、萃取、判斷語氣、寫結論，是由 AI 閱讀文字後完成的。Claude API 依處理的文字量計費，這筆費用付給 AI 服務，跟 Threads 無關。收集資料、統計數字這些用一般程式處理的部分不花 AI 費用。

### 帳號分析與關鍵字研究可以分開嗎？

可以，是兩個獨立功能，依需求擇一或一起使用；開發上也可以分開上線。

### 用自己的帳號和用客戶的帳號，差在哪？

| | 用自己的帳號（預設） | 請客戶授權（選配） |
| --- | --- | --- |
| 設定 | 授權一次，所有專案都能用 | 每個客戶都要自己登入授權 |
| 關鍵字研究 | 可以 | 可以（沒差別） |
| 客戶與競品帳號 | 只有公開資料 | 客戶帳號有完整資料；競品仍然只有公開資料 |
| 觀看數 | 看不到客戶的 | 看得到客戶的，可以算回覆率 |

**結論**：一般市調用自己的帳號就夠，客戶和競品都只用公開資料，比較基準一致。只有想精準判斷「客戶哪些貼文觸及多但沒人回應」時，才需要客戶授權。

### 報告怎麼呈現？

不需要 logo、不做簡報。依用途分成四層：

1. **結論卡**：一句話結論＋建議動作＋信心，一個畫面看完。
2. **核心表格**：內容主軸表、高互動公式表、競品對照表、市場缺口表等，用來查和比。
3. **少量圖表**：只在形狀比數字重要時才用，例如四象限圖、時段熱力圖、語氣刻度條（不用雷達圖）。
4. **證據**：任何數字都能點開看原始貼文。

輸出格式：網頁為主，可匯出 Markdown 與 Excel。

## 6. 不額外花錢的做法、網頁前台與資料累積（PRD v0.6）

### 在 VS Code 裡讓 AI 讀網頁、分析，為什麼還要傳給 Claude？

在 VS Code 用 Claude Code 分析，背後一樣是 Claude 在處理文字，只是計費方式不同：

| 方式 | 費用 | 限制 |
| --- | --- | --- |
| Claude API | 用多少付多少 | 可以自動化、給別人用 |
| **Claude Code + Pro／Max 訂閱** | **包含在月費中** | 每 5 小時一個額度週期，另有每週上限（與 claude.ai 共用）；只能自己用 |
| 本機開源模型 | 免費 | 中文、網路用語、反諷的理解較弱 |

另外，Anthropic 的條款不允許用 Pro／Max 訂閱替其他使用者處理請求，要做成給別人用的服務時必須改用 API。

### 為什麼不讓 AI 直接讀 Threads 網頁來收集？

- Claude Code 內建的讀網頁工具無法登入，也不會執行網頁程式，讀不到 Threads 的回覆。
- 改用自動操作瀏覽器登入捲動，技術上可行，但有違反服務條款、帳號被限制的風險。
- 讀整個網頁會浪費額度。

**決定**：收集交給一般程式（官方 API 或手動匯入），分析才交給 Claude。

### 三層分工

1. **一般程式（免費）**：統計、字數、時間、互動指數、基本去重、明顯閒聊過濾。
2. **本機模型（免費）**：分群、相似度比對。
3. **Claude Code（訂閱）**：類型判斷、欄位萃取、語氣判斷、主題命名、結論。

**個人版**：分析方法寫成專案中的 Claude Code 自訂指令（例如 `/analyze-thread`），在 VS Code 執行。之後要自動排程或給別人用時，再把引擎換成 API，資料格式與前台都不用改。

### 網頁前台怎麼累積資料

- **資料與呈現分開**：分析結果存成 JSON，網頁讀 JSON 即時畫出報告。改版時所有舊報告自動套用新樣式。
- **累積的東西**：報告庫、同一貼文的快照、同一帳號的每月分析、跨報告的洞察庫（工具總表、高互動公式庫、市場缺口庫）、使用者的標記與筆記。
- **兩個階段**：先做靜態網站（JSON 檔＋HTML），不需額外費用；報告多到數百份或需要在網頁上建立任務時，再加資料庫，前台不用重寫。
- **隱私**：留言原文不進 Git、到期刪除；分析結果長期保留且一般留言者匿名；網站不放在公開網址。
