## 1. 背景與問題

Threads 上一篇熱門貼文底下，常有數百到數千則留言，而且回覆會一層一層往下延伸。想了解「大家到底怎麼看這件事」時，只能手動往下滑、展開回覆，實際上會遇到幾個問題：

- **看不完**：留言量大，巢狀回覆要一個一個點開，很花時間。
- **看不全**：平台依演算法排序，容易只看到少數高讚留言，產生偏誤。
- **無法量化**：說不出支持和反對大概各占多少、主要論點有哪些、討論風向何時轉變。
- **無法留存**：貼文或留言可能被刪除或編輯，事後無從查證。

## 2. 產品目標

使用者只要貼上一篇 Threads 貼文的網址，系統就能**完整收集該貼文串（主文、串文、所有層級的回覆）**，並產出**結構化資料**與**分析報告**。

### 2.1 目標（Goals）

1. 輸入一個貼文網址，就能收集主貼文與全部可取得的回覆，並保留回覆樹狀結構。
2. 自動產出分析報告，內容包含：摘要、主題分群、情緒／立場分布、代表性留言、互動熱點與時間軸。
3. 原始資料可匯出（JSON / CSV），方便二次研究。
4. 同一貼文可重複收集（快照），並比較不同時間點的差異。

### 2.2 非目標（Non-Goals）

- 不做全站監聽或關鍵字大量爬取（MVP 只處理「單一貼文串」）。
- 不做自動回覆、發文或任何代替使用者在 Threads 上的互動行為。
- 不建立個人使用者側寫，也不提供跨貼文追蹤特定帳號的功能。
- 不繞過登入牆、私人帳號或平台的存取限制。

## 3. 目標使用者與情境

| 角色 | 情境 | 核心需求 |
| --- | --- | --- |
| 行銷／品牌小編 | 品牌貼文或競品貼文下的留言反應 | 快速知道正負評比例、客訴重點 |
| 內容創作者 | 分析自己爆文的留言 | 找出受眾關心的議題、下一篇題材 |
| 研究者／學生 | 研究某個公共議題的網路討論 | 完整、可引用、可匯出的原始資料 |
| 記者／編輯 | 追蹤爭議事件風向 | 時間軸、立場變化、代表性說法 |

### 使用者故事

- 身為小編，我想貼上一個網址，**5 分鐘內**拿到留言的情緒分布與前 5 大主題，才能馬上向主管回報。
- 身為研究者，我想下載**含回覆層級、時間、按讚數**的完整資料，才能用自己的工具分析。
- 身為創作者，我想看到**哪幾則留言引發最多二次討論**，才能了解爭議點在哪裡。
- 身為記者，我想比較**今天與三天前**的快照，才能看出風向和被刪除的留言。

## 4. 功能需求

優先級：P0 = MVP 必須、P1 = MVP 後第一波、P2 = 未來考慮

### 4.1 輸入與任務管理

| ID | 需求 | 優先級 |
| --- | --- | --- |
| F-01 | 支援貼上 Threads 貼文網址（`threads.net` / `threads.com` 的 `/@user/post/{code}` 格式），並驗證格式 | P0 |
| F-02 | 建立收集任務，顯示進度（已收集則數、目前深度、預估剩餘時間） | P0 |
| F-03 | 設定收集範圍：最大留言數、最大回覆深度、是否包含作者串文 | P1 |
| F-04 | 任務歷史列表，可重新開啟過去的結果 | P1 |
| F-05 | 排程重新收集（例如每 6 小時一次，持續 3 天） | P2 |

### 4.2 資料收集

| ID | 需求 | 優先級 |
| --- | --- | --- |
| C-01 | 收集主貼文：內文、作者、發文時間、媒體類型與連結、互動數（讚、回覆、轉發、引用） | P0 |
| C-02 | 收集作者本人的串文（同一作者連續回覆形成的 thread） | P0 |
| C-03 | 收集所有層級回覆，並保留 `parent_id`，以重建回覆樹 | P0 |
| C-04 | 每則回覆記錄：內文、作者帳號、時間、按讚數、回覆數、是否為原作者 | P0 |
| C-05 | 分頁與重試機制，遇到速率限制時自動退避（exponential backoff） | P0 |
| C-06 | 去重（同一則留言只存一次），並可從中斷處續傳 | P0 |
| C-07 | 快照版本：每次收集產生一個 snapshot，保留收集時間 | P1 |
| C-08 | 收集引用貼文（quote posts）作為延伸討論 | P2 |
| C-09 | 圖片 OCR，讓圖片中的文字也納入分析 | P2 |

### 4.3 分析功能

| ID | 需求 | 說明 | 優先級 |
| --- | --- | --- | --- |
| A-01 | 整體摘要 | 用 LLM 產生 3～5 段摘要：原文在說什麼、留言主要反應、爭議點 | P0 |
| A-02 | 基本統計 | 總留言數、參與人數、平均／最大深度、原作者回覆次數 | P0 |
| A-03 | 情緒分析 | 每則留言標記正面／中性／負面，呈現整體分布 | P0 |
| A-04 | 立場分析 | 相對於主貼文的觀點：支持／反對／中立／離題 | P0 |
| A-05 | 主題分群 | 將留言歸納成 5～10 個主題，每個主題附名稱、說明、則數、代表留言 | P0 |
| A-06 | 代表性留言 | 每個主題與立場各挑 3 則代表留言（兼顧讚數與代表性，不只挑最熱門的） | P0 |
| A-07 | 互動熱點 | 找出引發最多子回覆的留言（討論節點）與最高讚留言 | P0 |
| A-08 | 時間軸 | 留言數隨時間變化的曲線，並標示情緒／立場的變化 | P1 |
| A-09 | 關鍵詞／詞雲 | 中文斷詞（含繁簡）後的高頻詞與特徵詞 | P1 |
| A-10 | 快照比較 | 兩次快照的新增／刪除留言、統計差異、風向變化 | P1 |
| A-11 | 自訂提問 | 使用者用自然語言對這串資料提問（例如「有人提到價格嗎？」），回答需附上引用留言 | P1 |
| A-12 | 可疑行為提示 | 標出短時間大量相似留言、新帳號集中出現等異常模式（只提示，不下定論） | P2 |

**分析品質原則**

- 所有 LLM 產出的結論**必須能連回原始留言**（附留言 ID 或連結），避免無法查證的幻覺。
- 分類結果要附信心分數，信心低的歸為「無法判斷」，不硬塞進某一類。
- 報告須註明樣本限制，例如「本次收集到 812 / 顯示 1,034 則回覆」。

### 4.4 報告與匯出

| ID | 需求 | 優先級 |
| --- | --- | --- |
| R-01 | 網頁報告：摘要卡片、統計圖表、主題列表、代表留言、可展開的回覆樹 | P0 |
| R-02 | 匯出原始資料：JSON（樹狀）與 CSV（扁平，含 `parent_id` 與 `depth`） | P0 |
| R-03 | 匯出報告：Markdown / PDF | P1 |
| R-04 | 報告內可搜尋、依主題／立場／情緒篩選留言 | P1 |
| R-05 | 匯出時可選擇匿名化作者帳號（hash 化） | P1 |

## 5. 資料收集方案評估

資料來源是這個產品最關鍵的技術與合規風險，需在開發前完成評估。

| 方案 | 說明 | 優點 | 缺點／風險 |
| --- | --- | --- | --- |
| **A. Threads 官方 API（Meta）** | 透過 Threads API 的 OAuth 授權，取得貼文與回覆資料 | 合規、穩定、有正式欄位 | 權限範圍有限：完整回覆多半只限**自己帳號的貼文**；讀取他人公開內容的能力需依當時 API 權限（如關鍵字搜尋等）確認；有速率限制，也需要通過 App 審核 |
| **B. 公開頁面擷取** | 讀取未登入即可看到的公開頁面內容 | 可處理任意公開貼文 | 可能違反平台服務條款；頁面結構變動就會失效；未登入通常看不到完整回覆 |
| **C. 使用者端瀏覽器擴充功能** | 使用者在自己的瀏覽器中開啟貼文，由擴充功能讀取畫面上已載入的內容並上傳 | 資料是使用者本人看得到的內容；不需伺服器端爬蟲 | 需要使用者手動捲動／展開；仍需檢視服務條款；維護成本高 |
| **D. 手動匯入** | 使用者上傳自己整理的 JSON / CSV，或貼上文字 | 零合規風險，可立即使用 | 使用者自己整理很費工 |

**建議**

- **MVP**：採用 **A（官方 API，先支援「分析自己帳號的貼文」）+ D（手動匯入）**，確保合規，並讓分析引擎可以先開發、驗證。
- **第二階段**：由法務／合規確認後，評估 C（使用者端擴充功能）來支援他人公開貼文。
- **不建議**在未取得合規確認前，於伺服器端大量爬取（方案 B）。

> 待確認：Threads API 目前對「讀取他人公開貼文的完整回覆」的實際支援程度、所需權限與速率限制，需在技術評估（Spike）階段實測。

## 6. 資料模型

```text
Thread（貼文串）
├─ thread_id           平台貼文 ID
├─ url
├─ author_username
├─ text
├─ media[]             { type, url }
├─ created_at
├─ metrics             { likes, replies, reposts, quotes }
└─ snapshots[]

Snapshot（收集快照）
├─ snapshot_id
├─ thread_id
├─ collected_at
├─ source              api | extension | import
├─ reported_reply_count   平台顯示的回覆數
├─ collected_reply_count  實際收到的回覆數
└─ posts[]

Post（留言／回覆）
├─ post_id
├─ parent_id           回覆對象；直接回覆主文則為 thread_id
├─ root_id             = thread_id
├─ depth               1 = 直接回覆主文
├─ author_username     （可匿名化）
├─ is_op               是否為原作者
├─ text
├─ created_at
├─ like_count
├─ reply_count
└─ analysis            { sentiment, stance, topic_id, confidence, lang }

Topic（主題）
├─ topic_id
├─ snapshot_id
├─ label
├─ description
├─ post_count
└─ representative_post_ids[]
```

## 7. 系統架構（建議）

```text
[Web 前端] ──► [API 服務] ──► [任務佇列] ──► [Collector Worker]
                   │                              │ 官方 API / 匯入
                   │                              ▼
                   │                         [資料庫]（貼文、快照）
                   │                              │
                   └──────────────► [Analyzer Worker]
                                         │ 1. 前處理（清理、語言偵測、斷詞）
                                         │ 2. 逐則分類（情緒／立場，批次送 LLM）
                                         │ 3. Embedding + 分群 → LLM 命名主題
                                         │ 4. 統計、熱點、時間軸
                                         │ 5. 整體摘要（map-reduce，引用留言 ID）
                                         ▼
                                    [報告產生]
```

**技術重點**

- **LLM**：使用 Claude API 做分類、主題命名與摘要。逐則分類採批次處理並要求結構化輸出（JSON schema）；摘要則採 map-reduce，以處理數千則留言。
- **分群**：先以 embedding 分群（如 HDBSCAN / K-Means），再交由 LLM 命名與合併相似群，比純 LLM 分群更穩定、成本也更低。
- **中文處理**：支援繁體／簡體混用、注音文、表情符號與網路用語；斷詞可用 jieba 或 CKIP。
- **成本控制**：短留言或純表情留言可先用規則過濾；分析結果依 `snapshot_id` 快取，不重複計費。

## 8. 非功能需求

| 類別 | 需求 |
| --- | --- |
| 效能 | 1,000 則留言內：收集 ≤ 3 分鐘、分析 ≤ 3 分鐘（不含平台速率限制等待時間） |
| 規模 | 單一貼文串最多支援 10,000 則留言（MVP 上限可設 3,000） |
| 可靠性 | 收集任務可續傳；單則分析失敗不會讓整份報告失敗 |
| 準確度 | 情緒／立場分類與人工標註的一致率 ≥ 80%（以 200 則標註樣本驗收） |
| 成本 | 分析 1,000 則留言的 LLM 成本設定上限（例如 ≤ US$1），並在報告中顯示 |
| 安全 | API Token 加密儲存；使用者只能存取自己建立的任務 |

## 9. 隱私、合規與倫理

- **遵守平台條款**：優先使用官方 API；任何其他收集方式上線前，都需經過合規審查。
- **資料最小化**：只收集分析所需的欄位，不收集留言者的個人檔案、追蹤者等資訊。
- **匿名化選項**：報告與匯出預設可遮蔽帳號；對外分享的報告應強制匿名化。
- **保存期限**：原始資料預設保存 90 天，使用者可隨時刪除；刪除後同步清除分析快取。
- **刪除尊重**：快照比較雖可呈現「某則留言已刪除」，但不應在對外分享的報告中重現已刪除留言的全文（待確認政策）。
- **避免濫用**：不提供針對單一使用者的追蹤或側寫；可疑行為提示只呈現模式，不指控特定帳號。
- **AI 透明**：報告標註哪些內容由 AI 產生，並提醒可能有誤判。

## 12. 風險與對策

| 風險 | 影響 | 對策 |
| --- | --- | --- |
| 官方 API 無法取得他人貼文的完整回覆 | 可用情境受限 | MVP 先聚焦自己帳號＋手動匯入；第二階段評估合規的使用者端方案 |
| 平台條款或 API 政策變動 | 功能失效 | 收集層抽象成 adapter，可替換來源；持續關注開發者公告 |
| LLM 誤判反諷、梗圖、網路用語 | 分析失真 | 附信心分數與原文連結；加入「無法判斷」類別；以人工標註集持續評估 prompt |
| 大量留言造成成本與時間暴增 | 體驗差、成本高 | 設留言上限、規則預過濾、批次處理、結果快取 |
| 個資與隱私爭議 | 法律與聲譽風險 | 資料最小化、匿名化、保存期限、禁止個人追蹤功能 |

## 13. 待決問題

1. MVP 是否只支援「自己帳號的貼文」？還是一開始就必須支援任意公開貼文？
2. 產品形式：個人自用工具（CLI / 本機）還是多使用者 SaaS？會影響帳號、權限與成本設計。
3. 立場分析的「支持／反對」要相對於主貼文，還是讓使用者自訂議題與立場選項？
4. 報告是否需要對外分享連結？分享時的匿名化規則為何？
5. 是否需要支援多語言報告（中文為主，英文為輔）？
