## 1. 背景與問題

Threads 上一篇熱門貼文底下，常有數百到數千則留言，而且回覆會一層一層往下延伸。想了解「大家到底說了什麼」時，只能手動往下滑、展開回覆，實際上會遇到幾個問題：

- **看不完**：留言量大，巢狀回覆要一個一個點開，很花時間。
- **看不全**：平台依演算法排序，容易只看到少數高讚留言，產生偏誤。
- **無法整理**：留言裡的資訊是零散的，無法變成可比較、可統計的結構化資料。
- **無法留存**：貼文或留言可能被刪除或編輯，事後無從查證。

另外還有一個關鍵問題：**不同類型的貼文，想從留言裡得到的東西完全不同。**

| 貼文範例 | 真正想知道的 | 不太需要的 |
| --- | --- | --- |
| 「大家都用 Claude 做出了什麼工具？」 | 每個人做了什麼、解決什麼問題、怎麼做的、成果在哪 | 留言的情緒是正面還是負面 |
| 「我們新品上市了！」 | 正負評比例、客訴重點、購買意願 | 每則留言的技術細節 |
| 「遠端工作該不該取消？」 | 正反方各有哪些論點、論點強度 | 工具清單 |
| 「新手該學 Python 還是 JS？」 | 大家推薦什麼、理由、共識程度 | 情緒分布 |

如果所有貼文都套用同一套「情緒＋立場＋主題」分析，結果會像「87% 的留言是正面情緒」這種對研究沒有幫助的數字。因此，本產品的核心設計是**先判斷貼文類型，再決定研究方向與分析方法**。

## 2. 產品目標

使用者只要貼上一篇 Threads 貼文的網址，系統就能**完整收集該貼文串**，**判斷這篇貼文屬於哪一種討論類型**，並依類型採用對應的**分析模式**，產出能回答使用者真正研究問題的結構化資料與報告。

### 2.1 目標（Goals）

1. 輸入一個貼文網址，就能收集主貼文與回覆，並保留回覆樹狀結構；**依研究問題自動判斷要全量收集或抽樣收集**，確保資料完整又不浪費。
2. 自動判斷貼文類型，並推薦分析模式；使用者可以確認、改選，或自訂研究問題。
3. 每種分析模式有各自的研究問題、萃取欄位與報告模板，重點放在「從留言萃取出有用的資訊」，而不只是做統計。
4. 只保留與研究問題相關的內容：無關的問答與閒聊會被刪除，重複的內容會被合併。
5. 原始資料與萃取結果可匯出（JSON / CSV），方便二次研究。
6. 同一貼文可重複收集（快照），並比較不同時間點的差異。
7. （第二階段）支援**市調研究專案**：輸入關鍵字或帳號連結，自動找出相關貼文串，分析經營重點、發文方式、語氣與互動驅動因素，產出可以交給客戶的市調報告。

### 2.2 非目標（Non-Goals）

- 不做即時的全站監聽。關鍵字研究只透過官方搜尋介面取得有限範圍的貼文，並以研究專案為單位進行（見第 5 節）。
- 不做自動回覆、發文或任何代替使用者在 Threads 上的互動行為。
- 不建立個人使用者側寫。帳號經營分析只針對**公開的品牌、創作者、媒體帳號**的公開貼文內容，不推論帳號主或留言者的個人屬性（年齡、政治傾向、健康狀況等）。
- 不繞過登入牆、私人帳號或平台的存取限制。

## 3. 目標使用者與情境

| 角色 | 情境 | 常用分析模式 |
| --- | --- | --- |
| 開發者／社群經營者 | 發起「大家做了什麼」的徵集貼文，想整理成清單或文章 | 徵集／作品分享型 |
| 內容創作者 | 分析自己爆文的留言，找下一篇題材 | 提問求助型、意見討論型 |
| 行銷／品牌小編 | 品牌貼文或競品貼文下的留言反應 | 品牌／產品回饋型 |
| 研究者／學生 | 研究某個公共議題的網路討論 | 意見討論型、新聞事件型 |
| 記者／編輯 | 追蹤爭議事件風向 | 新聞事件型、意見討論型 |
| 行銷顧問／社群代操 | 幫客戶做主題市調，分析客戶或競品帳號的經營方式 | 研究專案（第 5 節） |

### 使用者故事

- 身為開發者，我發了一篇「大家用 Claude 開發出了什麼工具？」，我想**自動得到一份工具清單**，裡面有工具名稱、解決的問題、怎麼用 Claude 做的、連結，並且依用途分類，這樣我不用一則一則整理。
- 身為開發者，我也想知道**哪些工具最多人詢問或想要**，以及**大家提到但還沒人做的需求**，作為我下一個專案的靈感。
- 身為小編，我想貼上一個網址，**5 分鐘內**拿到留言的情緒分布與前 5 大客訴重點，才能馬上向主管回報。
- 身為行銷顧問，我輸入客戶產業的關鍵字或競品的帳號連結，想知道**市場在討論什麼、競品的經營重點、發文方式和語氣，以及什麼樣的貼文最能讓人回應**，並拿到可以直接交給客戶的建議。
- 身為研究者，我想下載**含回覆層級、時間、按讚數**的完整資料，才能用自己的工具分析。
- 身為記者，我想比較**今天與三天前**的快照，才能看出風向和被刪除的留言。

## 4. 核心機制：貼文類型判斷與分析模式

### 4.1 流程

```text
貼上網址
  │
  ▼
【預覽】收集主貼文 + 前 50 則回覆 + 平台顯示的總回覆數
  （這 50 則只用來判斷類型，不是最終分析資料）
  │
  ▼
【類型判斷】LLM 讀取主貼文與樣本回覆
  → 輸出：主要類型、次要類型（可選）、信心分數、判斷理由
  │
  ▼
【收集範圍判斷】依模式與總回覆數決定：全量收集／抽樣收集（見 4.2）
  │
  ▼
【使用者確認】顯示：
  「系統判斷這是『徵集／作品分享型』，將整理工具清單、用途分類…
    共 512 則回覆，此模式需要全量收集，預估 4 分鐘」
  → 使用者可以：✅ 確認 ／ 🔄 改選模式 ／ 🔄 改收集範圍 ／ ✏️ 自訂研究問題
  │
  ▼
依決定的範圍收集回覆
  │
  ▼
【內容篩選與去重】收錄／合併／排除（排除的留言刪除，見 4.3）
  │
  ▼
【通用分析】＋【模式專屬分析】
  │
  ▼
依模式套用報告模板
```

- 類型判斷**同時參考主貼文與回覆**：有些貼文本身是提問，但回覆實際上都是作品分享，這時應以回覆的實際內容為準。
- 可以同時套用**一個主要模式＋一個次要模式**，例如「徵集型為主，另外加上對 Claude 的評價分析」。主要與次要模式的收集範圍不同時，取較完整的那一個。
- 信心分數低於門檻（例如 0.6）時，不自動套用，而是列出 2～3 個候選模式讓使用者選擇。

### 4.2 收集範圍判斷：全量還是抽樣？

**判斷原則：看研究問題是「列舉型」還是「比例型」。**

| 研究問題性質 | 範例 | 需要的資料 | 收集範圍 |
| --- | --- | --- | --- |
| **列舉型**：想知道「有哪些」 | 大家做了哪些工具？有哪些論點？有哪些客訴？ | 每一則都可能是獨一無二的內容，漏收一則就少一筆資料 | **全量收集** |
| **比例型**：想知道「大概多少比例」 | 正面評價占多少？支持方多還是反對方多？ | 只要樣本有代表性，比例就會收斂，多收的資料不太會改變結論 | **抽樣收集** |

#### 各模式的預設收集範圍

| 模式 | 預設範圍 | 理由 |
| --- | --- | --- |
| M1 徵集／作品分享型 | **全量**（含所有層級的回覆） | 每則分享都是一個獨立的項目；工具細節常出現在深層的補充回覆中 |
| M2 提問求助型 | **全量** | 少數但有價值的答案常在長尾，按讚數少不代表不重要 |
| M3 意見討論／爭議型 | **全量** | 論點地圖需要完整；立場比例雖可抽樣，但攻防鏈需要完整的回覆樹 |
| M4 品牌／產品回饋型 | **抽樣**（使用者勾選「完整客訴清單」時改為全量） | 主要產出是情緒與面向的比例 |
| M5 新聞／事件反應型 | **抽樣**（使用者勾選「完整補充資訊」時改為全量） | 主要產出是反應分布與風向 |
| M6 經驗故事型 | **抽樣** | 主要產出是「有多少比例的人有類似經驗」 |
| 自訂模式 | 由 LLM 判斷研究問題屬於列舉型或比例型 | 例如「大家遇到哪些困難」→ 全量；「多少人覺得難」→ 抽樣 |

**通用規則（優先於上表）**

1. **總回覆數 ≤ 300 則時一律全量收集**：成本低，不值得冒抽樣誤差的風險。
2. 使用者永遠可以手動改成全量收集。
3. 報告開頭一定會標示這次用的是全量還是抽樣、收集了多少則、覆蓋率多少。

#### 抽樣收集的做法（比例型）

「前 50 則」對判斷情緒大方向通常夠用，但有兩個問題需要處理：

- **偏誤**：平台顯示的前 50 則多半是高讚或較早的留言，不一定能代表全體。例如早期留言通常比較正面，後期才出現批評。
- **誤差**：50 則樣本的比例誤差大約是 ±14%（95% 信心水準），只能看出大方向。

因此抽樣採用**以 50 則為起點的逐步加量**：

1. **起點**：先收 50 則。若資料來源允許，依時間與層級分層抽樣（早期／中期／晚期、第一層／深層回覆），而不是只取排在最前面的 50 則。
2. **加量**：每次再多收 50 則，重新計算各類比例。
3. **停止條件**（兩者都成立才停）：
   - 連續兩批加入後，各類比例的變化都小於 3 個百分點（結果已經穩定）；
   - 樣本數達到誤差 ±10% 所需的數量（約 100 則；總數較少時依有限母體修正，例如總數 500 則時約 80 則）。
4. **上限**：最多 400 則（約 ±5% 誤差）。超過就不再加量。
5. 資料來源無法分層、只能依平台順序收集時，報告要註明「樣本可能偏向高互動留言」。

#### 無法全量時的處理（列舉型）

若總數超過收集上限（例如 MVP 設 3,000 則），或受到速率限制無法全量收集：

- 採**飽和收集**：分批收集，並追蹤「每一批新發現的項目數」。當連續兩批（每批 100 則）的新項目都少於 5% 時，視為接近飽和。
- 報告中呈現**新項目發現曲線**與估計覆蓋率，讓使用者判斷清單是否夠完整。
- 使用者可以選擇之後繼續收集剩餘的部分（續傳）。

### 4.3 內容篩選與去重

#### 4.3.1 內容篩選：收錄／合併／排除

收集完成後，每則留言都會依**目前模式的研究問題**判斷處理方式：

| 處理 | 定義 | 範例（M1 徵集型） |
| --- | --- | --- |
| **收錄** | 包含研究問題需要的內容 | 「我用 Claude Code 做了一個自動記帳的 LINE Bot…」 |
| **合併** | 本身不是獨立內容，但為已收錄的項目補充了資訊 | 分享者回覆別人「用 Claude API 接 Google Sheets，大概花一個週末」→ 補進該工具的 `tech_stack`、`dev_effort` |
| **排除** | 與研究問題無關的內容 | 「怎麼做的？」「求連結」「好厲害」「+1」、標記朋友、純表情、廣告、離題閒聊，以及沒有補充任何項目資訊的問答來回 |

**排除的留言要刪除**：

- 排除的留言**不進入萃取、分析、報告與結果匯出**。
- 刪除前會先統計需要的訊號，例如「求連結」「我也想要」的次數會算進該工具的關注度，之後刪除內文，只留下數量。
- 為了避免誤刪，排除的留言會先暫存在「已排除」清單中，列出排除原因，讓使用者抽查、救回誤判的留言。使用者按下「確認清除」後，或報告產生 7 天後，永久刪除內文。
- 報告中顯示統計，例如「收集 512 則：收錄 176、合併 38、排除 298」。

**各模式的收錄標準**

| 模式 | 收錄 | 排除（範例） |
| --- | --- | --- |
| M1 徵集／作品分享型 | 分享一個具體項目（自己做的或推薦的）；開發心得與踩坑；「有沒有人做過 X」這類需求 | 追問、稱讚、求連結、單純的問答來回 |
| M2 提問求助型 | 提出答案、建議、解法，或有具體經驗的說明 | 「同問」「我也想知道」、與答案無關的追問 |
| M3 意見討論／爭議型 | 表達立場或提出論點、論據、反駁 | 純情緒發言（沒有論點）、人身攻擊、離題 |
| M4 品牌／產品回饋型 | 對產品或品牌的任何評價、需求、使用經驗 | 抽獎留言、標記朋友、與產品無關 |
| M5 新聞／事件反應型 | 反應、補充資訊、疑問 | 廣告、離題 |
| M6 經驗故事型 | 分享類似或不同的經驗、給建議 | 標記朋友、純表情 |

- 判斷時會一併提供**父留言與原貼文**作為上下文，避免把「回答別人問題時提供的工具細節」誤判成閒聊。
- 判斷不確定的留言（信心 < 0.6）預設**收錄並標記「待確認」**，寧可多收，不要誤刪。

#### 4.3.2 去重

| 層級 | 情況 | 處理 |
| --- | --- | --- |
| 1. 留言重複 | 同一則留言因分頁或續傳被收了兩次 | 依 `post_id` 去重 |
| 2. 內容重複 | 同一個人重複貼了相同內容 | 只保留一則，按讚與回覆數加總 |
| 3. 同項目、同作者 | 分享者把同一個工具分成好幾則留言說明 | 合併成一筆，各欄位整合，保留所有來源留言 |
| 4. 同項目、不同人 | 多人分享或推薦同一個工具／答案／論點 | 合併成一筆，記錄 `mention_count` 與所有來源 |

**比對方式**：名稱正規化（大小寫、全半形、空白）→ 連結比對（同一個 GitHub 或網站網址即視為同一項目）→ 語意相似度 → 相似度在邊界的案例交由 LLM 判斷。

- **不確定的情況不自動合併**：標記為「可能重複」，在報告中讓使用者一鍵合併或分開。
- 名稱相似但實際上是不同作品時（例如兩個人各自做了「記帳 Bot」），要保留成兩筆。判斷依據是作者不同，而且描述或連結也不同。

### 4.4 分析模式總覽

| 模式 | 判斷訊號（範例） | 核心研究問題 | 主要產出 |
| --- | --- | --- | --- |
| **M1 徵集／作品分享型** | 「大家做了什麼」「分享你的…」「推薦你用過的…」；回覆多是「我做了一個…」並附連結 | 大家做了／用了什麼？解決什麼問題？怎麼做的？ | 項目清單（結構化表格）、分類、做法與心得、需求缺口 |
| **M2 提問求助型** | 以問句求建議：「該選 A 還是 B？」「有人遇過…嗎？」 | 大家給了哪些答案？共識是什麼？理由是什麼？ | 答案排行、推薦理由、共識程度、分歧點 |
| **M3 意見討論／爭議型** | 表態或拋出議題：「我覺得…」「你們怎麼看…」；回覆有明顯正反方 | 有哪些立場？各自的論點與論據是什麼？ | 立場分布、論點地圖、主要攻防 |
| **M4 品牌／產品回饋型** | 品牌帳號發文、新品或活動公告、評論某產品 | 大家喜歡／不喜歡什麼？有什麼抱怨或期待？ | 情緒分布、優缺點、客訴、功能需求、購買意願、競品提及 |
| **M5 新聞／事件反應型** | 轉述新聞、突發事件、公告 | 大家如何反應？補充了哪些資訊？有哪些質疑？ | 反應類型、補充資訊與來源、疑點與謠言提示、時間軸 |
| **M6 經驗故事型** | 分享個人經歷：「我今天遇到…」 | 有多少人有類似經驗？有哪些共鳴或不同經歷？ | 類似經驗整理、共鳴點、建議與安慰類型 |
| **自訂模式** | 使用者自行輸入研究問題 | 由使用者定義 | 系統根據研究問題自動產生萃取欄位，使用者確認後執行 |

> 模式清單是可擴充的設定檔（見 4.7），之後可以新增模式，不需要改動程式架構。

### 4.5 通用分析（所有模式都做）

| ID | 需求 | 優先級 |
| --- | --- | --- |
| A-01 | 整體摘要：原文在說什麼、留言主要回應了什麼（摘要內容依模式調整重點） | P0 |
| A-02 | 基本統計：總留言數、參與人數、平均／最大深度、原作者回覆次數 | P0 |
| A-03 | 內容篩選與去重：依模式判斷收錄／合併／排除，排除的留言刪除；多層級去重（見 4.3） | P0 |
| A-04 | 互動熱點：引發最多子回覆的留言（討論節點）與最高讚留言 | P0 |
| A-05 | 時間軸：留言數隨時間的變化 | P1 |
| A-06 | 自訂提問：用自然語言對資料提問，回答需附上引用留言 | P1 |
| A-07 | 快照比較：兩次快照的新增／刪除留言與統計差異 | P1 |

**情緒分析與立場分析不再是預設項目**，改為模組，只在相關模式（M3、M4、M5）中啟用，或由使用者手動加選。

### 4.6 各模式詳細規格

每個模式都依相同格式定義：**研究問題 → 萃取欄位 → 分析方法 → 報告重點 → 淡化項目**。

#### M1 徵集／作品分享型（MVP 第一個模式）

以「大家用 Claude 開發出了什麼樣的工具？」為設計範例。

**研究問題**

1. 大家做出了哪些工具？各自解決什麼問題、給誰用？
2. 大家怎麼用 Claude 做的？用了哪些產品或功能、搭配什麼技術、花了多久？
3. 開發過程有哪些心得、技巧和踩坑經驗？
4. 哪些工具最受關注？（最多人按讚、詢問、要連結）
5. 有哪些需求被提出，但還沒有人做？

**萃取欄位（每一個被分享的項目一筆）**

| 欄位 | 說明 | 範例 |
| --- | --- | --- |
| `item_name` | 工具名稱（沒有名稱時由系統產生描述性名稱，並標記為「系統命名」） | 「發票自動記帳 Bot」 |
| `summary` | 一句話描述 | 拍照上傳發票，自動分類並寫入 Google Sheets |
| `problem_solved` | 解決的問題或動機 | 每月手動記帳太花時間 |
| `target_user` | 目標使用者 | 自己、家人、小型店家 |
| `category` | 用途分類（分群後自動命名） | 個人生產力／財務 |
| `claude_usage` | 如何使用 Claude（可多選） | Claude Code、Claude API、Claude.ai 對話、Artifacts、MCP、Agent SDK、其他 |
| `tech_stack` | 其他技術 | Python、LINE Bot、Google Sheets API |
| `dev_effort` | 開發時間或投入程度 | 一個週末 |
| `builder_background` | 開發者背景（僅限留言中本人提到的） | 非工程師、PM |
| `stage` | 階段 | 點子／開發中／自用／已上線／開源 |
| `links` | 連結 | GitHub、網站、影片 |
| `is_own_work` | 本人作品，或推薦別人的作品 | 本人 |
| `tips_pitfalls` | 心得、技巧、踩坑 | 「先讓 Claude 寫測試再寫功能比較穩」 |
| `source_post_ids` | 來源留言（可以有多則） | — |

**分析方法**

- **收集範圍**：預設全量收集，包含所有層級的回覆（見 4.2）。
- **內容篩選**：只收錄分享工具、開發心得和需求的留言；「怎麼做的？」「求連結」「好厲害」這類問答與閒聊一律排除並刪除，只把「求連結」等次數算進關注度（見 4.3.1）。
- **跨留言合併**：同一個工具的資訊常分散在同一作者的多則留言中，例如先分享工具，別人問「怎麼做的？」後才補充細節。系統要在同一個回覆子樹中，把同作者的後續回覆合併到同一個項目；別人的提問本身則被排除。
- **去重**：不同人分享同一個工具（例如都推薦同一個開源專案）時，合併成一個項目，並記錄提及次數（見 4.3.2）。
- **分類**：以 embedding 分群後，由 LLM 為每一類命名，例如「開發者工具」「個人生產力」「內容創作」「教育學習」「商業自動化」。
- **關注度評分**：綜合按讚數、子回覆數，以及子回覆中的「需求訊號」（例如「求連結」「我也想要」「可以開源嗎？」「怎麼做的？」）。
- **需求缺口**：萃取留言中「有沒有人做過 X？」「好希望有 X」這類尚未被滿足的需求，並比對是否已有人分享對應的工具。
- **心得彙整**：把 `tips_pitfalls` 分群，整理成「共同經驗」清單，並附上提及人數。

**報告重點**

1. 工具總覽：共收集到幾個工具、幾位分享者，分類分布圖
2. **工具清單表**：可排序、可篩選（依分類、Claude 使用方式、階段、是否有連結）
3. 分類深入：每一類的代表工具與共同特色
4. Claude 使用方式分布：例如 Claude Code 占 X%、API 占 Y%，以及常見的技術組合
5. 最受關注的工具 Top 10，附上關注理由
6. 開發心得與踩坑整理
7. 需求缺口／靈感清單
8. 附錄：可直接匯出成 Markdown，當作整理文章的初稿

**淡化項目**：整體情緒分布、立場分析。只有在留言明確評價 Claude 本身時，才以次要區塊「對 Claude 的評價」呈現。

#### M2 提問求助型

- **研究問題**：大家推薦什麼答案？理由是什麼？有沒有共識？
- **萃取欄位**：`answer`（推薦的選項或解法）、`reasons`、`conditions`（在什麼情況下適用）、`experience_based`（是否有親身經驗）、`caveats`
- **分析方法**：把相同的答案合併並計票（按讚加權）；找出共識與分歧；如果原作者有回覆「解決了」，則標示最終採用的答案。
- **報告重點**：答案排行、各答案的理由與適用情境、共識程度、少數但有價值的意見
- **淡化項目**：情緒分析

#### M3 意見討論／爭議型

- **研究問題**：有哪些立場？各自的論點與論據是什麼？攻防集中在哪裡？
- **萃取欄位**：`stance`、`claims`（論點）、`evidence`（論據類型：個人經驗／數據／引用來源／無）、`rebuts`（反駁哪一則）
- **分析方法**：立場分類（附信心分數）；論點分群；沿著回覆樹找出正反方的攻防鏈。
- **報告重點**：立場分布、論點地圖（各立場的前幾大論點）、最激烈的攻防串、有論據支撐與沒有論據支撐的比例
- **可選模組**：情緒分析（用來觀察討論是否失控）

#### M4 品牌／產品回饋型

- **研究問題**：大家喜歡和不喜歡什麼？有哪些抱怨、期待和購買意願？
- **萃取欄位**：`sentiment`、`aspect`（價格、品質、服務、設計…）、`complaint`、`feature_request`、`purchase_intent`、`competitor_mentions`
- **分析方法**：面向式情緒分析（aspect-based sentiment）；客訴分群；競品提及統計。
- **報告重點**：情緒分布、各面向的正負評、客訴 Top 5、功能需求、購買意願訊號、競品比較
- 這個模式就是 v0.1 的預設分析內容。

#### M5 新聞／事件反應型

- **研究問題**：大家如何反應？補充了哪些資訊？有哪些質疑？
- **萃取欄位**：`reaction_type`（驚訝／憤怒／支持／質疑／玩笑…）、`added_info`（補充資訊）、`sources`（引用的來源）、`questions`（疑問）
- **分析方法**：反應類型分布；補充資訊去重並列出來源；標示「未附來源的說法」（只提示，不判斷真假）。
- **報告重點**：反應總覽、補充資訊清單、主要疑問、時間軸（風向變化）

#### M6 經驗故事型

- **研究問題**：有多少人有類似經驗？大家的經歷有什麼共同點與不同？
- **萃取欄位**：`similar_experience`（是否有類似經驗）、`experience_summary`、`outcome`、`advice`
- **分析方法**：經驗分群、結果分類、建議彙整
- **報告重點**：類似經驗的比例、經驗類型、大家給的建議

#### 自訂模式

1. 使用者輸入研究問題，例如「我想知道大家用 AI 寫程式遇到最大的困難是什麼」。
2. 系統根據問題產生建議的萃取欄位與報告結構。
3. 使用者可以增減欄位，確認後執行。
4. 自訂好的模式可以另存為範本，下次重複使用。

### 4.7 模式的實作方式：分析模組 + 設定檔

每種模式都是由**分析模組**組合而成，並以設定檔定義，方便之後新增模式：

```yaml
# 範例：profiles/showcase.yaml
id: showcase
collection:
  strategy: full          # full | sample；總回覆數 ≤ 300 時一律 full
  question_type: enumeration   # enumeration（列舉型）| proportion（比例型）
name: 徵集／作品分享型
detect_hints:
  - 主貼文在徵求大家分享作品、工具、推薦
  - 多數回覆包含「我做了」「我用」並描述一個具體項目
research_questions:
  - 大家做出了哪些工具？解決什麼問題？
  - 怎麼用 Claude 做的？
  - 哪些最受關注？有哪些未被滿足的需求？
modules:
  - content_filter        # 通用：收錄／合併／排除，排除的刪除
  - item_extraction       # 依 schema 萃取項目
  - cross_reply_merge     # 合併同作者後續補充
  - dedupe                # 合併重複項目
  - clustering            # 分群與命名
  - interest_scoring      # 關注度評分
  - unmet_needs           # 需求缺口
  - tips_summary          # 心得彙整
extraction_schema: schemas/showcase_item.json
report_template: templates/showcase.md
optional_modules:
  - sentiment             # 使用者可手動加選
```

| 模組 | 說明 | 使用模式 |
| --- | --- | --- |
| `collection_planner` | 判斷全量或抽樣；抽樣時逐步加量並判斷是否收斂；全量無法完成時追蹤飽和度 | 全部 |
| `content_filter` | 依模式的收錄標準，把留言分為收錄／合併／排除，並在刪除前統計需求訊號 | 全部 |
| `item_extraction` | 依 JSON schema 從留言萃取結構化資料 | M1、M2、M4、M5、M6、自訂 |
| `cross_reply_merge` | 合併同一回覆子樹中同作者的補充說明 | M1、M2 |
| `dedupe` | 四層級去重；不確定的標記「可能重複」讓使用者決定 | 全部（層級 1～2）；M1、M2、M3（層級 3～4） |
| `clustering` | embedding 分群 + LLM 命名 | 全部 |
| `interest_scoring` | 按讚、子回覆、需求訊號綜合評分 | M1、M2 |
| `unmet_needs` | 萃取尚未被滿足的需求 | M1、M4 |
| `stance` | 立場分類 | M3 |
| `argument_mining` | 論點、論據與反駁關係 | M3 |
| `sentiment` / `aspect_sentiment` | 情緒／面向式情緒 | M4、M5（其他模式可選） |
| `timeline` | 時間序列 | M5（其他模式可選） |

## 5. 市調研究專案：從關鍵字或帳號出發

### 5.1 概念

第 4 節的功能一次分析「一篇」貼文串。幫客戶做市調時，需要分析的是「一個主題」或「一個帳號」底下的很多篇貼文。為此新增**研究專案**：

- 一個研究專案包含多篇貼文串，以及跨貼文的彙整分析。
- 每一篇貼文串仍然用第 4 節的引擎分析（類型判斷、收集範圍、內容篩選、去重），再往上一層做彙整。
- 研究專案是**第二階段功能**，會在單篇分析的 MVP 穩定後開發（見第 13 節）。

| 入口 | 輸入 | 回答的問題 |
| --- | --- | --- |
| **主題研究** | 一個或多個關鍵字、排除詞、時間範圍 | 市場上大家怎麼討論這個主題？關心什麼？哪些貼文最能引發討論？ |
| **帳號經營分析** | 一到五個帳號連結（客戶自己的或競品的） | 這個帳號的經營重點是什麼？怎麼發文、用什麼語氣？什麼樣的貼文最能讓人回應？ |

兩個入口可以串連：主題研究找到的高互動品牌帳號，可以一鍵加入帳號經營分析。

### 5.2 流程

```text
建立研究專案（客戶名稱、研究目的）
  │
  ├─ 輸入關鍵字 ──► 【擴充關鍵字】LLM 建議同義詞、俗稱、英文名稱、常見錯字，使用者勾選
  │                     │
  │                     ▼
  │                【探索】搜尋候選貼文（先取內文與互動數，不含回覆）
  │                     │
  │                     ▼
  │                【相關性判斷】排除同名不同義、廣告、離題的貼文
  │
  └─ 輸入帳號連結 ──► 【讀取帳號】期間內所有貼文與互動數
                        │
                        ▼
【挑選深入分析的貼文】依互動量與相關性排序，建議清單由使用者確認
  │
  ▼
【逐篇分析】每篇貼文串走第 4 節的流程
  │
  ▼
【跨貼文彙整】內容主軸、發文方式、語氣、互動驅動因素、市場缺口
  │
  ▼
【市調報告】附行動建議
```

### 5.3 主題研究（關鍵字入口）

**輸入**：關鍵字（可以多個）、排除詞、時間範圍（預設最近 30 天）、語言、探索上限（預設 500 篇）、深入分析篇數（預設 20 篇）

**步驟重點**

- **關鍵字擴充**：例如輸入「手搖飲」，建議「手搖」「飲料店」「珍奶」等詞，由使用者勾選。
- **相關性判斷**：LLM 閱讀每篇候選貼文，判斷是否真的在討論這個主題，例如分辨「蘋果」指的是水果還是 Apple。信心低的列入待確認清單。
- **挑選深入分析的貼文**：分數 = 相關性 × 互動量，其中**回覆數的權重最高**，因為要研究的是討論。為了避免結果被少數帳號主導，每個帳號最多選 3 篇。

**分析內容**

| 分析 | 說明 |
| --- | --- |
| 討論地圖 | 把所有相關貼文分群成子主題，列出每個子主題的貼文數、平均回覆數與趨勢 |
| 大家關心什麼 | 跨貼文彙整需求、痛點、疑問與推薦，來源是各篇貼文依模式萃取的結果 |
| 聲量趨勢 | 每天的相關貼文數與互動量 |
| 主要發聲帳號 | 相關貼文最多、互動最高的公開帳號。只列出品牌、創作者、媒體帳號；一般個人帳號只計入統計，不列出名稱 |
| 高互動貼文的共通點 | 用 5.4 D 的方法，找出這個主題下什麼樣的貼文最多人回應 |
| 市場缺口 | 大家在問但沒人好好回答的問題，以及大家在抱怨但沒人解決的痛點 |

**收集範圍**：探索階段屬於列舉型，在搜尋來源能提供的範圍內全量收集；深入分析的每篇貼文串依 4.2 的規則決定全量或抽樣。

### 5.4 帳號經營分析（帳號入口）

**輸入**：一到五個帳號連結，每個標記為「客戶」或「競品」；時間範圍（預設最近 90 天）或最近 N 篇（預設 100 篇）

**收集範圍**

- 帳號在期間內的**所有貼文**與互動數（列舉型，全量收集）。
- 回覆：互動最高的前 10 篇與最低的 5 篇，收集其回覆（依 4.2 的規則），用來分析「大家為什麼回應」。
- 期間內貼文**少於 30 篇**時，只做描述性整理，不做互動驅動分析，並在報告中說明原因。

#### A. 經營重點（內容主軸）

- 把貼文分群成**內容主軸**，例如「產品介紹」「幕後花絮」「產業觀點」「互動提問」「優惠活動」。
- 每個主軸列出：占比、平均互動、代表貼文。
- **主軸 × 互動矩陣**：找出「發很多但互動低」與「發很少但互動高」的主軸，作為調整建議。
- **商業目的分布**：導購、品牌形象、社群互動、知識分享各占多少。
- **說話對象**：根據貼文和回覆的內容，判斷帳號主要在對誰說話，例如「剛入門的新手開發者」「上班族媽媽」。只描述內容的溝通對象，不推論個別留言者的身分。

#### B. 發文方式

每篇貼文會萃取以下特徵：

| 特徵 | 內容 |
| --- | --- |
| 形式 | 純文字／單圖／多圖／影片／連結 |
| 長度 | 字數、段落數 |
| 串文 | 是否用多則串文展開 |
| 開頭方式 | 提問／數字／爭議觀點／個人故事／新聞時事／直接陳述 |
| 結尾方式 | 提問邀請回覆／徵集分享／導向連結／投票／沒有明確結尾 |
| 話題標籤 | 是否使用、用了哪些 |
| 發文時間 | 星期幾、時段 |
| 發文頻率 | 每週篇數、發文間隔 |
| 作者回覆習慣 | 作者在自己貼文底下回覆的比例、平均多久回覆、回覆的語氣 |

**產出**：發文習慣總覽、發文時段熱力圖（發文量與平均互動並列）、各形式的互動比較。

#### C. 語氣與風格

- **語氣向度**：每個向度以 1～5 分表示，並附上代表句：
  - 正式 ↔ 口語
  - 理性 ↔ 感性
  - 嚴肅 ↔ 幽默
  - 品牌腔（「我們」「小編」） ↔ 個人腔（「我」）
  - 保守 ↔ 大膽、敢表達立場
- **語言特徵**：emoji 使用頻率與常用 emoji、固定句式或口頭禪、中英夾雜、網路用語、排版習慣（換行、條列）。
- **風格指南**：用 3～5 條描述整理這個帳號的語氣，每條附範例句，可以直接給客戶的小編參考。
- 多帳號時，以雷達圖並列比較各帳號的語氣。

#### D. 什麼讓人想回應（互動驅動分析）

- **主要指標是回覆數**，因為目標是「讓更多人想回應」；按讚、轉發、引用作為輔助指標。
- **相對互動指數** = 該貼文的回覆數 ÷ 同帳號前後各 10 篇貼文回覆數的中位數。這樣可以排除粉絲數成長與帳號熱度起伏的影響，只比較貼文本身的表現。
- **特徵比較**：針對每個特徵，比較「有這個特徵」與「沒有這個特徵」的貼文的平均相對互動指數。例如：「以提問結尾的貼文，相對互動指數是其他貼文的 2.3 倍（有 18 篇、沒有 254 篇）」。
- **高低組輪廓**：另外列出相對互動指數前 20% 與後 20% 的貼文各有哪些常見特徵，作為補充。
- **回覆動機**：把高互動貼文底下的回覆分類成分享自身經驗、回答問題、表達認同、反駁、索取資訊、標記朋友、開玩笑等，看出貼文是「用什麼方式」讓人想回應。
  - 「標記朋友」在這裡是有意義的擴散訊號，會先計入動機統計，再依 4.3 的規則處理內文。
- **高互動公式**：整理成 3～5 條規則，每條都附數據、樣本數、代表貼文，以及信心等級。
  - 報告必須提醒**「相關不等於因果」**：例如提問結尾的貼文互動較高，也可能是因為那些貼文的主題本來就比較有話題性。
  - 有或沒有該特徵的任一組少於 10 篇時，不列入公式。

#### E. 競品比較（輸入多個帳號時）

- 並列比較各帳號的內容主軸、發文頻率、語氣雷達圖、平均相對互動，以及各自的高互動公式。
- 找出**差異化機會**，例如「競品都沒在做但受眾有反應的主軸」，或「客戶的語氣和競品太像」。

### 5.5 市調報告

報告結構：

1. **執行摘要**：3～5 個關鍵發現與建議
2. **市場討論**（主題研究）：討論地圖、大家關心什麼、聲量趨勢
3. **帳號經營重點**（帳號分析）：內容主軸、主軸 × 互動矩陣
4. **發文方式與語氣**：發文習慣、時段、風格指南
5. **什麼讓人想回應**：高互動公式、回覆動機
6. **競品比較與差異化機會**
7. **市場缺口與題材靈感**
8. **行動建議**：建議的題材、形式、語氣、發文時段，每一條都連回支持它的數據
9. **研究方法與限制**：資料來源、時間範圍、樣本數、覆蓋率、相關不等於因果的提醒

## 7. 資料收集方案評估

資料來源是這個產品最關鍵的技術與合規風險，需在開發前完成評估。

| 方案 | 說明 | 優點 | 缺點／風險 |
| --- | --- | --- | --- |
| **A. Threads 官方 API（Meta）** | 透過 Threads API 的 OAuth 授權，取得貼文與回覆資料 | 合規、穩定、有正式欄位 | 權限範圍有限：完整回覆多半只限**自己帳號的貼文**；讀取他人公開內容的能力需依當時 API 權限（如關鍵字搜尋等）確認；有速率限制，也需要通過 App 審核 |
| **B. 公開頁面擷取** | 讀取未登入即可看到的公開頁面內容 | 可處理任意公開貼文 | 可能違反平台服務條款；頁面結構變動就會失效；未登入通常看不到完整回覆 |
| **C. 使用者端瀏覽器擴充功能** | 使用者在自己的瀏覽器中開啟貼文，由擴充功能讀取畫面上已載入的內容並上傳 | 資料是使用者本人看得到的內容；不需伺服器端爬蟲 | 需要使用者手動捲動／展開；仍需檢視服務條款；維護成本高 |
| **D. 手動匯入** | 使用者上傳自己整理的 JSON / CSV，或貼上文字 | 零合規風險，可立即使用 | 使用者自己整理很費工 |

**建議**

- **MVP**：採用 **A（官方 API，先支援「分析自己帳號的貼文」）+ D（手動匯入）**。「用 Claude 做了什麼工具」這類徵集貼文通常是使用者自己發的，正好適合走官方 API。
- **第二階段**：由法務／合規確認後，評估 C（使用者端擴充功能）來支援他人公開貼文。
- **不建議**在未取得合規確認前，於伺服器端大量爬取（方案 B）。

> 待確認：Threads API 目前對「讀取他人公開貼文的完整回覆」的實際支援程度、所需權限與速率限制，需在技術評估（Spike）階段實測。

**研究專案的資料來源**

| 需求 | 優先方案 | 備案 |
| --- | --- | --- |
| 關鍵字找貼文 | 官方 API 的關鍵字搜尋功能（需申請對應權限並通過審核；回傳數量與可搜尋的時間範圍有限制，需實測） | 使用者貼上一批貼文網址，系統只做分析（半自動） |
| 讀取他人帳號的貼文 | 官方 API 讀取公開帳號資料與貼文的功能（權限範圍需實測） | 使用者貼上貼文網址清單；方案 C 瀏覽器擴充功能 |
| 讀取客戶自己帳號的貼文 | **請客戶以 OAuth 授權**：可以取得完整貼文與回覆，也可能取得觀看數等洞察數據，讓互動分析更準確 | 手動匯入 |

- 他人帳號通常只能看到公開的按讚、回覆、轉發數，**看不到觀看數**，因此互動分析以回覆數為主，並在報告中說明。

## 9. 系統架構（建議）

```text
[Web 前端] ──► [API 服務] ──► [任務佇列] ──► [Collector Worker]
                   │                              │ 官方 API / 匯入
                   │                              ▼
                   │                         [資料庫]（貼文、快照）
                   │                              │
                   │                    ┌─────────┴─────────┐
                   │                    ▼                   │
                   │           [Type Detector]              │
                   │           判斷類型 → 使用者確認          │
                   │                    │                   │
                   └──────────► [Analyzer Worker] ◄─────────┘
                                        │ 讀取 Profile 設定檔
                                        │ 1. 通用前處理與相關性過濾
                                        │ 2. 依 Profile 執行模組管線
                                        │    （萃取 → 合併 → 去重 → 分群 → 評分…）
                                        │ 3. 通用統計與熱點
                                        │ 4. 摘要（依模式調整重點，引用留言 ID）
                                        ▼
                                  [報告產生]（依 Profile 的模板）

研究專案（第 5 節）在上面的架構外再加兩個元件：

[Discovery Worker]    關鍵字搜尋／讀取帳號貼文 → 相關性判斷 → 建議深入分析清單
        │                    （選中的貼文串交給上面的 Collector / Analyzer 處理）
        ▼
[Project Aggregator]  貼文特徵萃取 → 內容主軸 → 互動驅動分析 → 競品比較 → 市調報告
```

**技術重點**

- **LLM**：使用 Claude API。類型判斷、萃取與分類一律要求結構化輸出（依 JSON schema）；摘要採 map-reduce，以處理數千則留言。
- **萃取時帶上下文**：萃取一則回覆時，一併提供它的父留言與原貼文，否則像「我也做了一個類似的」這種留言無法理解。
- **分群**：先以 embedding 分群，再交由 LLM 命名與合併相似群，比純 LLM 分群更穩定、成本也更低。
- **中文處理**：支援繁體／簡體混用、注音文、表情符號、網路用語與中英夾雜的技術名詞。
- **特徵萃取**：開頭方式、結尾方式、語氣等由 LLM 以結構化輸出判斷；字數、emoji、發文時間等用規則計算，不花 LLM 成本。
- **互動驅動分析用可解釋的統計**：分組比較與中位數，不用黑箱模型，這樣每條「高互動公式」都能說明依據，客戶也看得懂。
- **成本控制**：比例型模式採抽樣收集；內容篩選先排除無關留言；分析結果依 `run_id` 快取；更換模式時重用已收集的資料與 embedding。

## 11. 隱私、合規與倫理

- **遵守平台條款**：優先使用官方 API；任何其他收集方式上線前，都需經過合規審查。
- **資料最小化**：只收集分析所需的欄位，不收集留言者的個人檔案、追蹤者等資訊。
- **匿名化選項**：報告與匯出預設可遮蔽帳號；對外分享的報告應強制匿名化。M1 若要公開整理文章並標註作者，建議先取得分享者同意。
- **萃取不推測**：`builder_background` 這類與個人相關的欄位，只記錄本人在留言中主動提到的內容。
- **保存期限**：原始資料預設保存 90 天，使用者可隨時刪除；刪除後同步清除分析快取。
- **刪除尊重**：快照比較雖可呈現「某則留言已刪除」，但不應在對外分享的報告中重現已刪除留言的全文（待確認政策）。
- **避免濫用**：不提供針對單一使用者的追蹤或側寫。
- **帳號分析的對象限制**：只分析公開的品牌、創作者、媒體帳號；系統偵測到對象可能是一般個人帳號時，提醒使用者並要求確認研究目的。
- **報告中的留言者**：市調報告中引用的一般留言者一律匿名，只有公開的品牌、創作者、媒體帳號可以列名。
- **貼文草稿**（P-14）：產生的草稿只能參考風格，不得冒用其他帳號的身分或逐字複製其內容。
- **AI 透明**：報告標註哪些內容由 AI 產生，並提醒可能有誤判。

## 14. 風險與對策

| 風險 | 影響 | 對策 |
| --- | --- | --- |
| 官方 API 無法取得他人貼文的完整回覆 | 可用情境受限 | MVP 先聚焦自己帳號＋手動匯入；第二階段評估合規的使用者端方案 |
| 類型判斷錯誤，套用了不適合的模式 | 報告抓錯重點 | 分析前由使用者確認；信心低時列出候選模式；可更換模式重新分析且不用重新收集 |
| 貼文屬於混合類型 | 單一模式不夠用 | 支援主要＋次要模式；自訂模式補足 |
| 萃取時 LLM 自行補完沒提到的資訊 | 資料失真 | schema 允許空值、要求附來源留言、以無幻覺率指標持續驗證 |
| 同一項目的資訊分散在多則留言 | 清單不完整或重複 | `cross_reply_merge` 與 `dedupe` 模組；以人工標註集驗證 |
| 抽樣只取到平台排前面的留言，結果有偏誤 | 情緒或比例失真 | 分層抽樣；無法分層時在報告中註明；抽樣結果以全量資料回測 |
| 列舉型模式漏收留言 | 清單不完整 | 列舉型預設全量；無法全量時做飽和收集並顯示覆蓋率；支援續傳 |
| 把有用的補充內容誤判為閒聊而刪除 | 資料遺失 | 判斷時提供上下文；不確定時預設收錄；排除的留言先暫存 7 天，可救回 |
| 名稱相同但實際不同的項目被錯誤合併 | 清單失真 | 同時比對作者、描述與連結；不確定時不自動合併，交由使用者決定 |
| 平台條款或 API 政策變動 | 功能失效 | 收集層抽象成 adapter，可替換來源；持續關注開發者公告 |
| LLM 誤判反諷、梗圖、網路用語 | 分析失真 | 附信心分數與原文連結；加入「無法判斷」類別 |
| 大量留言造成成本與時間暴增 | 體驗差、成本高 | 設留言上限、相關性預過濾、批次處理、結果快取 |
| 個資與隱私爭議 | 法律與聲譽風險 | 資料最小化、匿名化、保存期限、禁止個人追蹤功能 |
| 關鍵字搜尋或讀取他人帳號的 API 權限申請不到，或限制太多 | 研究專案無法自動探索 | 備案：使用者貼上貼文網址清單（半自動）；客戶自己的帳號改用 OAuth 授權 |
| 把相關當成因果，給出錯誤建議 | 客戶照做卻沒效果 | 每條公式附樣本數與信心；報告明確提醒相關不等於因果；建議以 A/B 方式小規模驗證 |
| 貼文數太少，分析結論不穩定 | 結論失真 | 少於 30 篇不做互動驅動分析；有／沒有該特徵的任一組少於 10 篇時不列入公式 |
| 帳號熱度或粉絲數變化造成互動偏誤 | 誤判好貼文 | 相對互動指數以前後 10 篇的中位數為基準 |
| 語氣判斷主觀 | 客戶不信服 | 以向度分數呈現並附代表句；用人工標註校準 |
| 被用來分析一般個人帳號 | 隱私與倫理風險 | 限定公開的品牌、創作者、媒體帳號；偵測到個人帳號時提醒並要求確認研究目的 |

## 15. 待決問題

1. MVP 是否只支援「自己帳號的貼文」？還是一開始就必須支援任意公開貼文？
2. 產品形式：個人自用工具（CLI / 本機）還是多使用者 SaaS？
3. M1 的萃取欄位是否要依貼文主題再細分？例如「用 Claude 做的工具」需要 `claude_usage`，但「推薦的咖啡廳」需要地點與價位。建議做法：M1 內建通用欄位，再由類型判斷時根據主貼文**動態加入主題專屬欄位**，並讓使用者確認。
4. M1 整理出的工具清單若要公開發表，是否需要內建「通知分享者／取得同意」的流程？
5. 是否需要支援多語言報告（中文為主，英文為輔）？
6. 排除留言的永久刪除時間預設 7 天是否合適？是否需要「完全不暫存、立即刪除」的選項？
7. 抽樣的停止門檻（變化 < 3 個百分點、誤差 ±10%、上限 400 則）是否要開放使用者調整？
8. 研究專案要先做「帳號經營分析」還是「主題研究」？目前建議先做帳號分析，因為客戶授權自己帳號的資料來源最確定。
9. 客戶是否願意授權自己的帳號？授權後可能取得觀看數，互動分析會更準確。
10. 市調報告是否需要白標（顧問或客戶的 logo）與簡報格式？
11. 研究專案是否需要依客戶收費或計算成本（例如每個專案的 LLM 成本上限）？
